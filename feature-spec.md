# Feature Spec — AI Copilot ремонта

## 1. Назначение документа

Документ описывает первую продуктовую версию сервиса AI Copilot ремонта.

Фокус MVP: помочь пользователю быстро понять реальную стоимость ремонта, получить смету, план работ, подбор материалов и проверить смету подрядчика.

---

## 2. Проблема

Пользователь не контролирует ремонт:

- не понимает реальную стоимость работ и материалов;
- не знает, какие этапы нужны;
- не умеет проверять сметы подрядчиков;
- боится переплат и скрытых доплат;
- не понимает, где можно экономить, а где нельзя;
- не доверяет мастерам и подрядчикам.

Главная боль: **потеря контроля над бюджетом и качеством ремонта**.

---

## 3. Цель фичи

Дать пользователю независимую оценку ремонта до начала работ.

Пользователь должен получить:

- ориентировочную стоимость ремонта;
- структуру расходов;
- список работ;
- список материалов;
- план этапов;
- риски;
- рекомендации по экономии;
- проверку сметы подрядчика, если она уже есть.

---

## 4. Основной пользовательский сценарий

1. Пользователь открывает сервис.
2. Выбирает сценарий:
   - рассчитать ремонт;
   - проверить смету подрядчика;
   - подобрать материалы;
   - получить план ремонта.
3. Заполняет короткий бриф.
4. Загружает фото/видео помещения или файл сметы.
5. ИИ анализирует данные.
6. Сервис формирует предварительный отчет.
7. Пользователь видит краткий результат бесплатно.
8. Для детального отчета пользователь оплачивает тариф.
9. Пользователь получает полный отчет.
10. После отчета сервис предлагает:
    - подобрать материалы;
    - проверить подрядчика;
    - найти исполнителя;
    - подключить сопровождение ремонта.

## 5. MVP Scope

### Входит в MVP

#### 5.1. Онбординг

Поля:

- город;
- тип объекта;
- тип ремонта;
- площадь;
- количество комнат;
- помещение: ванная, кухня, комната, вся квартира;
- желаемый бюджет;
- желаемый стиль;
- сроки;
- наличие дизайн-проекта;
- наличие сметы подрядчика;
- фото/видео помещения.

#### 5.2. AI-диагностика ремонта

Функция определяет:

- тип ремонта;
- примерный объем работ;
- сложность;
- возможные риски;
- недостающие данные;
- вопросы для уточнения.

#### 5.3. Генерация сметы

Смета должна включать:

- демонтаж;
- черновые работы;
- электрика;
- сантехника;
- отделка;
- чистовые материалы;
- черновые материалы;
- доставка;
- непредвиденные расходы;
- резерв бюджета.

Для каждой позиции:

- название работы/материала;
- единица измерения;
- количество;
- цена за единицу;
- итоговая стоимость;
- комментарий;
- уровень уверенности.

#### 5.4. План работ

План должен включать:

- этап;
- описание;
- примерную длительность;
- зависимости;
- риски;
- критерий готовности этапа.

#### 5.5. Подбор материалов

Для каждой категории материалов сервис предлагает 3 уровня:

- эконом;
- оптимум;
- красиво/выше среднего.

Для товара:

- название;
- категория;
- цена;
- количество;
- ссылка;
- почему подходит;
- возможная альтернатива.

#### 5.6. Проверка сметы подрядчика

Пользователь загружает файл или текст сметы.

Сервис анализирует:

- завышенные цены;
- дублирующиеся позиции;
- пропущенные работы;
- странные формулировки;
- необоснованные объемы;
- позиции без единиц измерения;
- слишком низкие цены, которые могут привести к доплатам.

Результат:

- общий риск сметы;
- список подозрительных позиций;
- рекомендации по вопросам подрядчику;
- ориентир справедливой цены;
- вывод: принимать / торговаться / переделать смету.

#### 5.7. Итоговый отчет

Формат отчета:

- web-страница;
- PDF;
- markdown/Notion-compatible текст.

Структура отчета:

1. Краткий вывод.
2. Общий бюджет.
3. Разбивка по работам.
4. Разбивка по материалам.
5. План этапов.
6. Риски.
7. Где можно экономить.
8. Где нельзя экономить.
9. Список вопросов подрядчику.
10. Рекомендации следующих шагов.

## 6. Не входит в MVP

- мобильное приложение;
- полноценный 3D-редактор;
- AR-примерка интерьера;
- свой маркетплейс подрядчиков;
- escrow-платежи;
- гарантия ремонта;
- автоматическое заключение договора;
- управление бригадой;
- закупка материалов внутри сервиса;
- складская логистика;
- полноценная CRM для подрядчиков.

## 7. Персоны

### 7.1. Собственник квартиры

Цель: понять стоимость ремонта и не переплатить.

Боли:

- не разбирается в ремонте;
- боится обмана;
- не знает, какую смету считать нормальной;
- хочет контролировать бюджет.

### 7.2. Покупатель новостройки

Цель: быстро понять бюджет ремонта после покупки квартиры.

Боли:

- нет опыта;
- ограниченный бюджет после ипотеки;
- много решений сразу;
- нужно планировать закупки.

### 7.3. Владелец квартиры под аренду

Цель: сделать ремонт быстро, дешево и окупаемо.

Боли:

- важна экономика;
- нельзя переплачивать за дизайн;
- нужны практичные материалы;
- важны сроки.

### 7.4. Пользователь со сметой подрядчика

Цель: проверить, не завышена ли смета.

Боли:

- не понимает позиции;
- не знает рыночных цен;
- боится подписать невыгодный договор;
- хочет аргументы для переговоров.

## 8. User Stories

### Расчет ремонта

Как пользователь, я хочу указать параметры квартиры, чтобы получить примерный бюджет ремонта.

Acceptance Criteria:

- пользователь может заполнить бриф за 3–5 минут;
- сервис показывает диапазон стоимости;
- сервис объясняет, из чего складывается цена;
- сервис показывает уровень точности расчета.

### Проверка сметы

Как пользователь, я хочу загрузить смету подрядчика, чтобы понять, где меня могут обмануть.

Acceptance Criteria:

- можно загрузить PDF, Excel, изображение или текст;
- сервис извлекает позиции сметы;
- сервис подсвечивает рисковые позиции;
- сервис дает вопросы для подрядчика;
- сервис дает итоговый вывод.

### Подбор материалов

Как пользователь, я хочу получить список материалов под мой бюджет, чтобы не искать все вручную.

Acceptance Criteria:

- материалы разбиты по категориям;
- у каждого материала есть цена и количество;
- есть минимум 2–3 ценовых варианта;
- есть ссылки на покупку;
- итоговая сумма совпадает с бюджетом.

### План работ

Как пользователь, я хочу видеть порядок работ, чтобы понимать, что и когда должно происходить.

Acceptance Criteria:

- этапы идут в правильной последовательности;
- у каждого этапа есть длительность;
- указаны зависимости;
- указаны риски и критерии готовности.

## 11. AI-функциональность

### 11.1. Анализ фото

Задачи:

- определить тип помещения;
- найти видимые проблемы;
- оценить состояние отделки;
- предложить уточняющие вопросы.

Ограничение:

- результат не является строительной экспертизой;
- для скрытых дефектов нужна проверка специалиста.

### 11.2. Генерация сметы

ИИ использует:

- данные брифа;
- типовые нормы работ;
- региональные коэффициенты;
- базу цен;
- выбранный уровень отделки.

### 11.3. Объяснение сметы

ИИ должен объяснять каждую крупную статью простым языком:

- почему это нужно;
- можно ли убрать;
- какие риски экономии;
- как проверить подрядчика.

### 11.4. Проверка сметы подрядчика

ИИ сравнивает смету с типовыми диапазонами и правилами.

Результат должен быть не просто “дорого”, а:

- какая позиция вызывает вопрос;
- почему;
- какой нормальный диапазон;
- что спросить у подрядчика.

## 13. Risk Scoring

Сервис должен рассчитывать риск ремонта.

Факторы:

- старый фонд;
- неизвестное состояние коммуникаций;
- мокрые зоны;
- перенос электрики;
- сжатые сроки;
- слишком низкий бюджет;
- отсутствие проекта;
- смета без детализации;
- подрядчик без договора;
- большой аванс.

Шкала:

- 0–30: низкий риск;
- 31–60: средний риск;
- 61–100: высокий риск.

## 14. Acceptance Criteria MVP

MVP считается готовым, если:

- пользователь может пройти бриф;
- сервис формирует бесплатный предварительный расчет;
- пользователь может оплатить полный отчет;
- сервис формирует детальную смету;
- сервис формирует план работ;
- сервис формирует список материалов;
- пользователь может загрузить смету подрядчика;
- сервис выдает аудит сметы;
- отчет можно экспортировать;
- все расчеты имеют дисклеймер о приблизительности.

## 16. Ограничения и дисклеймеры

Сервис не должен обещать точную финальную стоимость ремонта.

Обязательные дисклеймеры:

- расчет является предварительным;
- финальная стоимость зависит от состояния объекта;
- скрытые дефекты могут изменить бюджет;
- сервис не заменяет техническое обследование;
- рекомендации по материалам зависят от наличия и актуальных цен;
- проверка сметы не является юридической экспертизой договора.

## 17. Edge Cases

### Неполные данные

Если пользователь не знает площадь или тип ремонта, сервис должен:

- предложить диапазоны;
- задать уточняющие вопросы;
- показать низкий уровень уверенности.

### Плохие фото

Если фото недостаточно информативны:

- запросить новые фото;
- показать, какие ракурсы нужны;
- не делать уверенных выводов.

### Слишком низкий бюджет

Если бюджет нереалистичен:

- честно показать, что ремонт не помещается в бюджет;
- предложить урезанный сценарий;
- выделить обязательные и необязательные работы.

### Смета без структуры

Если смета подрядчика плохо оформлена:

- распознать доступные позиции;
- отметить низкую надежность анализа;
- рекомендовать запросить детализацию.

### Пользователь хочет ремонт под ключ

На MVP не обещать выполнение ремонта.

Ответ:

- сначала дать смету и план;
- потом предложить проверенных подрядчиков, если доступно.

## 21. Definition of Done

Фича считается завершенной, если:

- пользователь может пройти путь от брифа до отчета;
- расчет занимает не больше 5 минут для пользователя;
- отчет понятен без помощи менеджера;
- есть платный сценарий;
- есть ручная проверка для снижения ошибок;
- отчет можно отправить пользователю;
- метрики событий настроены;
- есть юридические дисклеймеры;
- есть критерии качества сметы.

## 22. Главный принцип продукта

Пользователь платит не за ИИ и не за красивую картинку.

Пользователь платит за снижение риска:

- не переплатить;
- не ошибиться с материалами;
- не попасть на плохого подрядчика;
- не потерять контроль над ремонтом.
