# AGENTS.md

## Назначение проекта

Smetana AI — проект для разработки AI-слоя, который помогает пользователю быстрее находить функции, инструкции, документы, статусы и настройки в личном кабинете.

Главная продуктовая цель: снизить количество обращений в поддержку за счёт умного поиска, навигации и объяснений внутри продукта.

Проект не должен превращаться в автономного финансового агента. Базовый фокус — безопасный AI-помощник для поиска, навигации и read-only сценариев.

## Контекст продукта

Целевые пользователи:

- владелец бизнеса;
- бухгалтер;
- оператор;
- администратор;
- разработчик.

Ключевые пользовательские задачи:

- найти нужную функцию в личном кабинете;
- понять, как выполнить действие;
- найти документ, статус, настройку или раздел;
- разобраться в коротком или неоднозначном запросе;
- найти функцию по пользовательскому названию, даже если оно не совпадает с названием в интерфейсе.

## Основные принципы работы агентов

1. Сначала уточняй продуктовую задачу, затем предлагай техническое решение.
2. Делай минимальные, проверяемые изменения.
3. Не добавляй лишнюю архитектуру без явной необходимости.
4. Не придумывай API, данные, роли и бизнес-правила без источника в репозитории или задаче.
5. Все изменения должны быть объяснимы с точки зрения пользовательской боли и метрики.
6. При конфликте между скоростью и безопасностью выбирай безопасность.

## Ограничения по AI-функциям

Запрещено без отдельного явного решения:

- выполнять финансовые операции от имени пользователя;
- создавать, отменять или изменять платежи автономно;
- менять юридически значимые данные;
- подписывать документы;
- управлять доступами без подтверждения администратора;
- выполнять write-действия без понятного подтверждения, RBAC и audit log;
- выдавать неподтверждённую информацию как факт.

Разрешённый MVP-фокус:

- AI-поиск по личному кабинету;
- навигация к нужному разделу;
- объяснение, где находится функция;
- подсказки по how-to сценариям;
- поиск справочных материалов;
- объяснение статусов и ошибок;
- read-only просмотр данных при наличии прав.

## Требования к UX

Ответ AI должен быть:

- коротким;
- прикладным;
- с конкретным следующим шагом;
- без канцелярита;
- без уверенных ответов при нехватке данных;
- с явным указанием, если нужно действие пользователя или подтверждение.

Предпочтительный формат ответа помощника:

1. Краткий ответ на вопрос.
2. Куда нажать или что сделать.
3. Что произойдёт дальше.
4. Когда обращаться в поддержку.

## Продуктовые метрики

При проектировании фич учитывай влияние на:

- contact rate в поддержку;
- self-service rate;
- time to resolution;
- долю успешных поисковых сессий;
- долю переходов из AI-подсказки в нужный раздел;
- CSAT после AI-взаимодействия;
- количество повторных обращений по той же теме.

## Технические ожидания

Пока структура проекта не зафиксирована, агент должен:

- не создавать сложную структуру папок без необходимости;
- предпочитать простые и читаемые решения;
- добавлять README или документацию, если появляется новая логика;
- не хранить секреты в репозитории;
- не коммитить `.env`, токены, ключи, cookies, дампы персональных данных;
- использовать mock-данные только с явной пометкой;
- отделять продуктовую логику от экспериментальных прототипов.

## Работа с кодом

Перед изменениями:

- проверь существующую структуру проекта;
- найди релевантные файлы;
- оцени, есть ли уже похожая логика;
- не переписывай большие части без причины.

После изменений:

- проверь форматирование;
- запусти доступные тесты или проверки;
- если тестов нет, явно укажи, что проверить вручную;
- опиши, что изменилось и почему.

## Стиль задач и pull request

Issue должна содержать:

- пользовательскую боль;
- сценарий;
- ожидаемое поведение;
- ограничения;
- метрику успеха;
- критерии приёмки.

Pull request должен содержать:

- краткое описание изменения;
- ссылку на issue, если есть;
- что проверено;
- риски;
- скриншоты или примеры, если меняется UX.

## Критерии готовности

Изменение считается готовым, если:

- решает конкретную пользовательскую задачу;
- не нарушает ограничения безопасности;
- не добавляет неподтверждённые бизнес-правила;
- понятно, как проверить результат;
- есть минимальная документация для следующего разработчика или агента.

## Приоритеты

1. Безопасность и контроль действий.
2. Понятность для пользователя.
3. Снижение нагрузки на поддержку.
4. Простота реализации.
5. Масштабируемость только после подтверждения ценности.
